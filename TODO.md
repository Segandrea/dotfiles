## 1. Paradigm & Tooling Shifts (Long-Term Alternatives)

Currently, this repository uses **Bash (`install.bash`) + GNU Stow + `dconf` dump**. Depending on how you want to evolve your setup, here are the strongest alternatives for your Fedora + GNOME + terminal workflow:

- [ ] **Option A: [Chezmoi](https://www.chezmoi.io/) (Best drop-in upgrade over GNU Stow)**
  - **Templating:** Cleanly handle machine-specific values (`hornet`, `HDMI-2`, Lenovo `conservation_mode`, git email) in a single repo (`{{ if eq .chezmoi.hostname "hornet" }}`).
  - **No symlink fragility:** Writes real files and tracks drift (`chezmoi diff`) instead of relying on symlinks or `stow --adopt && git reset --hard`.
  - **Declarative scripts (`run_onchange_`):** Re-run package installations or `dconf load` only when the package list or `settings.ini` hash actually changes.

- [ ] **Option B: [Nix + Home Manager](https://nix-community.github.io/home-manager/) (Best for reproducible CLI & user-space on Fedora)**
  - **Declarative user-space:** Pin and build all CLI tools (`starship`, `fzf`, `zoxide`, `bat`, `neovim`, `tmux` + plugins, `fd`, Nerd Fonts), shell configs, completions, and even GNOME `dconf` settings via `flake.lock`.
  - **Eliminates manual bootstrapping:** No need for COPRs (`atim/starship`), TPM auto-clone in `tmux.conf`, or static completion scripts committed to Git.
  - **Trade-off:** System-level Fedora tweaks (RPMFusion, `mesa-va-drivers`, Flatpaks) still live outside Home Manager; Nix has a learning curve and uses extra disk space (`/nix/store`).

- [ ] **Option C: Fedora Atomic (Silverblue) + [BlueBuild](https://blue-build.org/) / Containerfile**
  - **Immutable custom OS image:** Build your entire Fedora setup (RPMFusion, multimedia codecs, OpenH264, `pop-shell`, CLI packages, Terra repo) automatically in GitHub Actions into a custom OCI image.
  - **Instant recovery:** Reproducing or recovering a broken system becomes a single `bootc switch` / `rpm-ostree rebase`, and the base OS never drifts mid-update.

- [ ] **Option D: Ansible (Likely overkill for a single desktop)**
  - Great idempotency (`ansible.builtin.dnf`, `community.general.flatpak`, `community.general.dconf`), but YAML playbooks are much more verbose and slower to iterate on than a modular Bash script + `justfile` or Chezmoi for a single workstation.

## 2. Architectural Refactors (Keeping Bash + GNU Stow)

If you keep your current **Bash + Stow** stack, these structural refactors will give the biggest boost to speed, reliability, and maintainability:

- [ ] **Separate `.bash_profile` / `environment.d` from `.bashrc`**
  - **Move exports out of `.bashrc`:** Currently `env.bash` is sourced in `.bashrc`, so every subshell or new Tmux pane re-runs the `PATH` loop and `mkdir -p` checks. Moving environment variables (`XDG_*`, `EDITOR`, `PATH`) to `~/.bash_profile` or `~/.config/environment.d/*.conf` makes them available to GUI apps and the entire GNOME Wayland session.
  - **Guard Tmux auto-attach in `.bashrc`:** Launching Tmux unconditionally in `bash/.bashrc` (lines 34–41) hijacks *every* interactive shell (including JetBrains/VS Code integrated terminals, `ssh` sessions, or `:term` inside Neovim). Either configure Alacritty to launch Tmux directly in `alacritty.toml` (`[terminal.shell]`), or guard the `.bashrc` block with `[[ "$TERM_PROGRAM" == "alacritty" || "$TERM" == "xterm-kitty" ]]`.

- [ ] **Speed up shell startup by lazy-loading `nvm` and `sdkman` (or switching to `mise` / `fnm`)**
  - Sourcing `nvm.sh` and `sdkman-init.sh` in `bash/.bashrc` (lines 46–51) adds hundreds of milliseconds of latency to every new Tmux pane/window.
  - Either replace them with **[mise](https://mise.jdx.dev/)** / **[fnm](https://github.com/Schniz/fnm)** (Rust-based, near-zero startup overhead) or wrap `nvm`/`sdkman` in lazy-loading functions that only source them when first invoked.

- [ ] **Replace `launchStartupScripts.bash` with `systemd --user` services and timers**
  - Instead of `autostart/.config/autostart/startupscripts.desktop` calling `launchStartupScripts.bash` in a sequential loop, stow native systemd user units into `~/.config/systemd/user/` (e.g., `random-wallpaper.service`/`.timer`, `screenlock-watcher.service`).
  - Gives you automatic crash restarts (`Restart=on-failure`), proper logs (`journalctl --user -u ...`), and non-blocking parallel startup.

- [ ] **Split `install.bash` into modular subcommands (or add a `justfile` / `Makefile`)**
  - Refactor `install.bash` into discrete functions (`setup_dnf`, `setup_codecs`, `install_cli`, `install_flatpaks`, `stow_dotfiles`, `load_dconf`) with a CLI dispatcher so you can run `./install.bash stow` or `./install.bash packages` without running the entire bootstrap from scratch.

- [ ] **Curate `settings.ini` instead of dumping root `/` in `dconf`**
  - `dconf dump /` currently captures noisy machine/transient state in `settings.ini`: GTK file-chooser pixel window sizes (lines 473–500), specific Bluetooth MAC addresses (`dev_F8_4E_17_78_50_9D` on line 321), and `welcome-dialog-last-shown-version='45.1'` (line 318).
  - Replace the `dconfdump` alias with a script that dumps only specific subtrees (`/org/gnome/desktop/interface/`, `/org/gnome/desktop/wm/keybindings/`, `/org/gnome/settings-daemon/plugins/media-keys/`, `/org/gnome/shell/extensions/`).

- [ ] **Lazy-load Bash completions via XDG `bash-completion` directory**
  - `bash/.config/bash/completions.bash` eagerly sources 6 completion files (`angular`, `cargo`, `npm`, `nvm`, `rustup`, `tmux`) on every shell startup, and committed snapshots go stale over time.
  - Placing or generating completions in `~/.local/share/bash-completion/completions/<command>` allows `bash-completion` to lazy-load them on demand the first time you press `<Tab>` for that command.
